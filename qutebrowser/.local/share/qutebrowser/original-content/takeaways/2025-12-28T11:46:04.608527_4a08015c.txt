EXPLOITING WEB SHELLS: PHP, .NET AND TOMCAT
INTRODUCTION

A web shell is a script or program used by attackers to obtain remote access and control over a server for malicious purposes. It acts as a clandestine gateway, providing unauthorized individuals with a remote command-line interface to the server, and enabling them to execute commands, upload or download files, and perform various actions on the compromised system. This tutorial aims to explore the mechanisms behind web shells, how to exploit them, and mitigation strategies that administrators can implement to safeguard against exploiting web shells.

How Do Web Shells Work?

Most programming languages used in web development enable the execution of system commands and external processes through functions like system() or exec(). While this is not by itself a vulnerability, attackers can manipulate the parameters passed to these functions, thereby identifying entry points through command injection or file upload vulnerabilities. This enables them to execute commands on the target host by passing arguments through the script. This is followed by establishing a persistent mechanism on the server for remote access and finally attempting to escalate privileges and leverage the backdoor to infiltrate organizations or exploit resources.

Web Shells Vs Reverse Shells

Web shells and reverse shells have precisely the same purpose: to allow remote shell access to a system. However, they use different methods to circumvent typical limitations such as firewalls:

For reverse shells, the connection is established from the server to an attacker-controlled endpoint.

Most firewalls do not block outgoing network traffic from the server, and such connections work directly even with Network Address Translation (NAT).

For web shells, the connection is established to a web page.

If the system serves web pages, it cannot block web access, so the attacker is always able to connect.

Types of Web Shells

There are two types of web shells.

One requires the web browser as the client – in this case, the web browser displays an interface that lets the user send commands to the operating system and view the results.

The other requires a client script and looks like a typical command-line console.

It uses HTTP to send commands to the shell installed on the server, receives responses, and displays them in the console.

Web shells may be written in any programming language that the web server supports and runs. Most are developed in PHP due to its popularity, but you can find them in ASP, Python, Perl, Ruby, and Unix. For this scenario, we choose to focus on PHP, ASP.NET and JSP by exploiting the Apache Tomcat server.


1. PHP WEB SHELLS

PHP web shells are a specific category of web shells written in PHP scripting language and majorly use the PHP inbuilt functions to execute commands.

The following are some of the common functions used to execute shell commands in PHP.

System()

The System() function executes an external program and displays the output.

The one-liner PHP code executes the ls -la command to list files and directories in the current directory in Linux systems.

<?php

//Returns the listing of the directory where the file runs (windows)
 system("ls -la");
?>


System() function output:

http://192.168.125.103/ls.php
Exec()

The exec() function accepts a command as a parameter but does not output the result by default. If a second optional parameter is specified, the result will be returned as an array. Otherwise, only the last line of the result will be shown if echoed.

<?php
 // Executes but returns nothing 
echo exec("ls -la");
?>

Exec() function output:

http://192.168.125.103/exec.php
Shell_exec()

The shell_exec() function is similar to exec(). However, it executes a command in the shell and returns the complete output of the command as a string.

It's useful when you want to capture the output of a command and use it within your PHP script.

It returns the output of the command, but it doesn't display it directly to the output buffer (browser or console) unless you explicitly print or echo the result.

<?php
// Executes the command "ls -la" in the shell and captures the output
$output = shell_exec("ls -la");

// Output the result to the browser
echo $output;
?>


shell_exec function output:

http://192.168.125.103/shell-exec.php
Passthru()

The passthru() function in PHP executes the command specified by the argument and directly passes the raw output to the output buffer. This means it will display the output directly to the user's browser without any PHP processing.

http://192.168.125.103/passthru.php
<?php
 // Execute the command and display raw output 
passthru("ls -la"); 
?>

3. EXPLOITING .NET APPLICATIONS TO OBTAIN A SHELL

From the previous attempts, web shell and injection attacks cut across all programming languages. In the .NET ecosystem, which encompasses a rich set of frameworks, libraries, and tools for building various types of applications, the threat of webshells is particularly pertinent. .NET applications, including web applications built with ASP.NET, are susceptible to webshell attacks if proper security measures to handle user inputs are not in place.

In this scenario, we delve into the creation and exploration of a .NET web shell. We'll explore how attackers may leverage vulnerabilities in .NET MVC web applications to implant and execute web shells, as well as the potential impact of such compromises on the security and integrity of the target system.

Workflow in .NET MVC

The .NET MVC (Model-View-Controller) application architecture is a structured approach for developing web applications in the .NET ecosystem. It divides the application into three interconnected components:

The Model - is responsible for managing data and business logic

The View - handles the presentation layer and renders the user interface

The Controller - serves as the intermediary to process user requests, execute actions, and coordinate interactions between the Model and the View.

The workflow of .NET MVC involves routing requests, processing them through controllers, rendering views, and sending responses back to clients. With that in mind, it is important to structure how you enumerate the MVC applications.

Go ahead and open the Visual Studio Code shortcut on the Desktop to access the provided application source code.

Routing:

Incoming requests are matched to route patterns defined in the application's route configuration.

Routes direct requests to the appropriate controller action based on the URL and HTTP method.

Controller Processing:

The controller receives the request, processes input data and performs necessary business logic.

It interacts with the model layer to retrieve or manipulate data.

View Rendering:

The controller selects an appropriate view template and passes data to it.

The view renders the UI using the provided data and generates HTML markup.

Response Sent to Client:

The generated HTML response is sent back to the client's browser for display.

Command Injection in .NET Applications

In .NET applications, code injection vulnerabilities often arise from improper handling of user input, especially in scenarios involving dynamic construction of commands or queries.

Let's examine a vulnerability in a .NET application.

Exploiting the Vulnerability

This sample app is quite naive in the way it handles user input. It simply accepts any input and concatenates it into a command to be executed by the underlying OS. An attacker could craft a malicious URL to exploit the vulnerability.

We will use the payload below to demonstrate this:

https://192.168.125.104:7008/Report/generate/777&&whoami>whoami.txt

The shell operator && serves as a logical AND and ensures the subsequent command is executed only if the preceding commands are executed. That is the command that creates a file/report with the name 777 and then executes the second part of the request.
whoami > whoami.txt retrieves the username of the currently logged-in user and stores it in a text file named whoami.txt. This command consists of two components: whoami, a system command that prints the current user's username, and the > operator, which redirects the output of the whoami command to a file.

Open the Reports folder to view the generated reports and the subsequent file whoami.txt

Summary

Code injection vulnerabilities pose significant risks to the security and integrity of .NET applications. By understanding common attack vectors, implementing secure coding practices, and conducting thorough security assessments, organizations can mitigate the risks associated with code injection and build more resilient and secure .NET applications. Generally speaking, you should never blindly trust any information that comes from the outside of your app. That includes data from web forms, URL parameters, and data from POST/PUT/PATCH requests to API endpoints as this is what attackers would be eyeing.

How to Prevent Web Shells and Code Injections

If you’re using PHP, disable potentially dangerous PHP functions such as exec(), shell_exec(), passthru(), system(), show_source(), proc_open(), pcntl_exec(), eval(), and assert(). To do that, add a disable_functions directive in your php.ini. Of course, this is only practical if you don’t use these functions in your web applications.

Sanitize all user inputs.

If any of your web applications allow file uploads to the web server, make sure that you only permit uploading for whitelisted file types. Take care to verify uploads not only based on file extensions but also by checking file content on the server side for potential malicious payloads.

Configure a web application firewall (WAF) to your internet-facing server, to block attempts to upload malicious files.
